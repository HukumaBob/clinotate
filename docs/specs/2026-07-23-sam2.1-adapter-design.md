# SAM 2.1 adapter + API selection mechanism

Status: approved, not yet implemented. Follows Phase 2a.1 (UI/UX design,
done) — see [ROADMAP.md](../../ROADMAP.md)'s Phase 2b entry for the open
question this resolves.

## Why

The frame editor's UI/UX design
([2026-07-23-platform-ui-ux-design.md](2026-07-23-platform-ui-ux-design.md))
already specifies two model tabs, SAM-3 and SAM 2.1, sharing one surrounding
UI, with SAM 2.1 as the default tab and the only tab exposing a Mask
prompt-input. That design left the backend/API side of the split explicitly
unresolved. This spec closes that gap and designs the SAM 2.1 adapter itself.

## Facts confirmed against installed/reference source before this design

(Per this project's own hard-earned rule: README/memory is not sufficient —
see `.superpowers/sdd/task-6-report.md`/`task-7-report.md` for the prior
incidents this guards against.)

- **`sam2`/`facebookresearch/sam2`'s real `SAM2ImagePredictor.predict()`**
  (read from `/mnt/ntfsdisk/segmentation/medical_segmentation/segment-anything-2/sam2/sam2_image_predictor.py`)
  accepts `mask_input: np.ndarray` — a low-res (1×256×256) mask logit array,
  typically from a previous `predict()` call's `low_res_masks` output. It is
  a refinement input layered on top of point/box, not a standalone
  from-scratch prompt: `_prep_prompts`/`_predict` pass points, boxes, and
  mask together into `sam_prompt_encoder`.
- **`SAM2VideoPredictor`** (same reference tree, `sam2_video_predictor.py`)
  exposes `add_new_points_or_box()` and `add_new_mask()` as separate calls —
  a given frame takes either points/box OR a mask, never both
  (`_run_single_frame_inference` asserts `point_inputs is None or
  mask_inputs is None`). `propagate_in_video(inference_state,
  start_frame_idx=None, max_frame_num_to_track=None, reverse=False)` is a
  generator that walks **one direction per call** — bidirectional tracking
  from an anchor frame is two sequential calls on the same
  `inference_state` (`reverse=False` then `reverse=True`), not a single
  call.
- **The installed `sam3` package (not just this project's adapter) has no
  mask-prompt input at all**, confirmed by reading both prompt entry points
  inside the `ml-worker` container
  (`/app/.venv/lib/python3.12/site-packages/sam3/model/`):
  `sam3_video_inference.py`'s `add_prompt()` accepts only
  `text`/`points`/`bounding_boxes`, and `sam3_image_processor.py`'s
  `Sam3Processor` only exposes `set_text_prompt`/`add_geometric_prompt`
  (point/box). So the UI spec's "SAM 2.1 adds a Mask prompt-input that SAM-3
  does not have" is a verified fact, not the unverified hypothesis it was
  when the UI spec was written — nothing about that part of the UI needs
  revisiting.
- **License**: `facebook/sam2.1-hiera-large` (code and weights) is Apache
  2.0 — unlike SAM-3's custom Meta SAM License. `NOTICE` already has a
  preliminary note about this from a prior session; this spec's
  implementation plan updates the wording (SAM2 → SAM 2.1, "not yet used" →
  "in use").
- **Weights source**: `pip install git+https://github.com/facebookresearch/sam2`
  (no PyPI package, same git-install pattern already used for `sam3` in
  `ml-worker/Dockerfile`), checkpoint `facebook/sam2.1-hiera-large` via
  `SAM2ImagePredictor.from_pretrained(...)` / `SAM2VideoPredictor.
  from_pretrained(...)`. Cached under the existing `ml_worker_hf_cache`
  Docker volume (`docker-compose.yml`, mounted at
  `/root/.cache/huggingface`) — no new volume needed, HF's default cache
  location already lands there.

## Decisions

### 1. API shape: parallel SAM2 endpoints, symmetric to SAM-3

Rejected alternatives: a single endpoint with a `model` discriminator field
(would force reworking the already-working, already-tested SAM-3 routes to
share a schema), and using the design spec's generic `Job.payload =
{"adapter": "<name>", ...}` string directly (loses per-adapter Pydantic
validation — e.g. `mask_input` only makes sense for SAM 2.1 — pushing that
check into ad hoc runtime logic instead of the type system).

- `JobType.SAM2_PREDICT = "sam2_predict"`, `JobType.SAM2_TRACK =
  "sam2_track"` added to the existing enum (`backend/app/jobs/models.py`).
  `SAM3_PREDICT`/`SAM3_TRACK` unchanged.
- `Sam2PredictRequest`/`Sam2TrackRequest` added to `backend/app/jobs/schemas.py`,
  separate from `Sam3PredictRequest`/`Sam3TrackRequest`.
- `PromptIn.type` widens from `Literal["point", "box"]` to `Literal["point",
  "box", "mask"]` (shared by both request schemas — SAM-3's router simply
  never receives `"mask"` from the frontend for its own tab; if it ever did,
  `Sam3Adapter`'s existing `_prompt_to_geometric_box` still raises
  `ValueError` for it, same failure mode as any other unrecognized type
  today). For `type="mask"`, `coords` is unused; a new `mask_png: str`
  field (base64-encoded PNG) carries the mask.
- New routes `/jobs/sam2/predict`, `/jobs/sam2/track` in
  `backend/app/jobs/router.py`; `enqueue_sam2_predict`/`enqueue_sam2_track`
  in `backend/app/jobs/service.py`, mirroring the existing
  `enqueue_sam3_predict`/`enqueue_sam3_track`.
- Celery task names: `sam2_predict`, `sam2_track` (symmetric to
  `sam3_predict`/`sam3_track`, as already preferred in the prior session).

### 2. Mask-prompt payload: raw PNG from the frontend

Rejected alternative: passing only a reference to an existing saved
Annotation mask. Rejected because it only covers refining an
already-existing annotation, not the UI spec's "draw a rough mask" gesture
(a fresh freehand mask drawn on canvas, never persisted as its own
Annotation).

The frontend sends a raw rough-mask PNG (arbitrary size, user-drawn) as
base64 in `PromptIn.mask_png`. `Sam2Adapter` is responsible for decoding,
resizing to 256×256, binarizing, and converting to mask logits (±32) before
calling `SAM2ImagePredictor.predict(mask_input=...)` — mirroring the same
resize-and-threshold conversion `SAM2VideoPredictor.add_new_mask()` already
does internally for the video path, since no public low-level helper for
this exists in the reference `sam2` package. The frontend contract stays a
plain PNG — it does not need to know about the 256×256/logit internals of
either predictor.

### 3. `Sam2Adapter` (`ml-worker/app/sam2_adapter.py`)

A new class, not a subclass of `Sam3Adapter` — the two share no model state,
only the lazy-load/evict *pattern* already established by `Sam3Adapter`.

- `predict(frame_bytes: bytes, prompts: list[dict]) -> MaskResult`: lazily
  builds a `SAM2ImagePredictor`, calls `set_image()`, converts this
  project's `point`/`box`/`mask` prompt dicts into `point_coords`/
  `point_labels`/`box`/`mask_input` kwargs for `.predict()`. Points/boxes
  from multiple prompts combine into one call the way SAM's own multi-point
  refinement works; a `mask` prompt supplies `mask_input` alongside any
  point/box in the same request (matching `SAM2ImagePredictor.predict`'s
  real signature, which accepts all three together).
- `track(frames: list[bytes], prompts: list[dict], anchor_frame_index: int,
  backward: int, forward: int) -> list[MaskResult]`: one `init_state()`
  (temp-dir bridge, same `tempfile.TemporaryDirectory` + numbered-PNG
  pattern as `Sam3Adapter.track()` — reusing the existing `StorageService`→
  local-temp-file bridge, not reinventing it), one
  `add_new_points_or_box()`/`add_new_mask()` call on `anchor_frame_index`
  (whichever prompt type was supplied), then up to two sequential
  `propagate_in_video()` calls on the same `inference_state`: `reverse=False,
  max_frame_num_to_track=forward` and `reverse=True,
  max_frame_num_to_track=backward`, each skipped when its count is `0` (per
  the UI spec's "`0` in either field means don't track that direction").
  Frames outside the requested backward/forward window are not included in
  the result list — this task only tracks the requested range, unlike
  SAM-3's `track()` which always propagates across every input frame.
- Same `_clear_cuda_cache_on_error` context-manager pattern as
  `sam3_adapter.py` (`gc.collect()` + `torch.cuda.empty_cache()` on any
  exception) wraps both methods' bodies.
- `_release_image_predictor()`/`_release_video_predictor()` mirror
  `Sam3Adapter`'s existing release methods (drop reference, `gc.collect()`,
  `empty_cache()`).

### 4. GPU eviction: one shared slot-manager in `tasks.py`

Rejected alternative: having `Sam2Adapter` and `Sam3Adapter` import each
other and call each other's release methods directly. Works for two
families but creates a cyclic dependency between what should be independent
model families — doesn't scale if a third segmentation adapter is ever
added.

`ml-worker/app/tasks.py` keeps its existing per-family singletons
(`_adapter_singleton` for `Sam3Adapter`, a new `_sam2_adapter_singleton` for
`Sam2Adapter`) plus a single module-level "current GPU slot" tracker with
four possible values: `sam3_image`, `sam3_video`, `sam2_image`, `sam2_video`.
Before any of the four lazy-getters
(`Sam3Adapter._get_processor`/`_get_video_predictor`,
`Sam2Adapter`'s two equivalents) builds its model, it evicts whichever of
the *other three* slots is currently occupied by calling that slot's
existing release method — reusing the already-proven
`_release_video_predictor`/`_release_processor` pattern from
`sam3_adapter.py`, extended to cover all four slots instead of just the two
within one adapter. This is a superset of what `Sam3Adapter` already does
internally for its own two models, now coordinated across both adapter
instances from `tasks.py` rather than duplicated inside each adapter.

Self-restart-after-track-failure
(`_restart_worker_process_after_track_failure` + `docker-compose.yml`'s
`restart: unless-stopped`) is reused unchanged and applies to
`run_sam2_track` exactly as it already does to `run_sam3_track` — a track()
GPU failure on either adapter poisons the process the same way.

### 5. Stability re-test before trusting `predict()`

Before considering SAM 2.1's `predict()` production-ready, repeat the
micro-jitter stability test that caught SAM-3's 1-2px instability: the same
visible lesion in
`/home/hukuma/Pictures/references/High_Grade_Displasia_Stomach01.jpg`,
point prompts shifted by 1-2px in a short series, confirm the resulting mask
does not change. This is a manual/exploratory check during implementation,
not a unit test — recorded here so the implementation plan doesn't skip it.

## Explicitly out of scope

- Any change to the already-approved frame editor UI/UX — this spec is
  backend/adapter only.
- SAM-3's existing code path — no refactor, rename, or behavior change.
- A third segmentation adapter or generalizing the adapter-registry pattern
  beyond what's needed for exactly two adapters — YAGNI until a third
  adapter is actually proposed.
